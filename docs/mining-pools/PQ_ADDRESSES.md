# CHCQ addresses and post-quantum payouts

Source: [`crypto/addresses.py`](../../src/chipcoin/crypto/addresses.py), [`crypto/pq/schemes.py`](../../src/chipcoin/crypto/pq/schemes.py), [`crypto/pq/mldsa.py`](../../src/chipcoin/crypto/pq/mldsa.py), [`consensus/pq_activation.py`](../../src/chipcoin/consensus/pq_activation.py), [`consensus/validation.py`](../../src/chipcoin/consensus/validation.py), and [`NodeService.build_candidate_block`](../../src/chipcoin/node/service.py). Reference release commit `12e4dbc8974bd76885e30e6dacdf1b7be898e126`.

A CHCQ address is ASCII `CHCQ` followed by Base58Check of 34 payload bytes: version `0x50` (1), signature scheme ID `0x0a` for ML-DSA-44 (1), and `SHA3-256(raw public key bytes)` (32). The checksum is the first four bytes of double-SHA256 of that payload. The raw ML-DSA-44 public key is **1,312 bytes**; a signature is **2,420 bytes**. An address contains a commitment, not the public key itself. Parse `CHCQ` before `CHC` because the prefixes overlap. Validate the Base58 alphabet, payload length, version, checksum and scheme ID; address parsing alone does not prove control of the key.

The same CHCQ textual encoding is used across network profiles. **Network separation is enforced by consensus context and signing domain**, not by an address prefix unique to each network. Transaction v2 signing includes `chipcoin:tx-signature:v3:<chain_id>` in the canonical preimage; a pool should keep Mainnet, Testnet and Devnet wallets and chain data separate. The pinned native ML-DSA-44 backend is used for real transaction signing/verification. The test-only SHAKE helper in `mldsa.py` is **not** a production signature scheme.

| Network | CHCQ output support activation height | Coinbase maturity | Pool implication |
| --- | ---: | ---: | --- |
| Mainnet | 0 | 100 | Use controlled CHCQ payout addresses and ML-DSA-44 for subsequent v2 spends. |
| Testnet | 20,000 | 20 | A CHCQ template request below activation is rejected. |
| Devnet | 30,000 | 10 | Early isolated tests require a legacy address; this does not model Mainnet PQ payouts. |

The template API checks the **candidate block height** and rejects an early CHCQ payout with HTTP 400 `invalid_request`. Consensus independently checks output activation and Mainnet's PQ transaction policy. Ancestor `4c0984e` could issue a Mainnet template for a checksum-valid CHCQ address with unsupported scheme ID `0x0b`, which consensus would reject. The release includes fix `15b8b190ee44b6e4ed3b8817bcf10a252f2a1e37`: a Mainnet payout using a scheme other than ML-DSA-44 now fails before template issuance with HTTP 400 `invalid_request`. The positive/negative regression is [`test_mainnet_template_rejects_chcq_scheme_rejected_by_consensus`](../../tests/integration/pool/test_block_submission.py). Pool software should still validate scheme ID `0x0a` itself and never treat an issued template as proof of consensus validity. Do not change a network's activation height to simplify integration tests. The [address vector](test-vectors/v1.json) is a public test fixture; never pay real coins to it.

Separately, Julien reports that [Crypto Connection](https://crypto-connection.net) Miningcore Chipcoin module v6.1 has enforced worker authorization with CHCQ address version `0x50` and ML-DSA-44 scheme ID `0x0a` since **2026-11-24 21:22 UTC**. That check is a pool login policy; the Core's address and consensus checks remain independent. Other pools must define and verify their own worker-admission policy.

For non-Python clients, implement the address codec above or call a reviewed library with identical Base58Check and SHA3-256 semantics; no C/Go SDK is claimed here. Independently compare outputs to the [fixture verifier](test-vectors/verify.py) and the canonical Python parser before accepting real payouts. Signature generation/verification must use an ML-DSA-44 implementation interoperable with the pinned Core backend; address validation by itself is insufficient for transaction signing.
