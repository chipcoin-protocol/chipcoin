# Stratum translation boundary

Tagged Chipcoin Core v0.1.2 offers HTTP mining methods, **not a Stratum server**. A pool backend must translate its worker protocol to the template, canonical block builder, and submission APIs. [Crypto Connection](https://crypto-connection.net) and its operator Julien supplied the backend details below and authorized attribution. The [Crypto Connection Miner](https://github.com/gacanga/crypto-connection-miner) is an external GPL-3.0 project. Its public client source was reviewed locally at clean commit `6d40215d6e070c3022e8abc7380e5b969b98e7ad`, tagged `v0.10.2`; the historical pool test used miner v0.10.1. These are distinct evidence points. The pool server source and worker traffic were not available. Treat backend details as **operator-reported deployment behavior**, not an audited server implementation or an official Chipcoin Stratum standard. Do not copy external GPL code into Core without a separate license review.

| Pool responsibility | Core boundary |
| --- | --- |
| Worker connection, authorization, subscriptions, job IDs, reconnect policy | None; private pool service |
| Share difficulty and vardiff | Pool-chosen threshold; Core supplies network `bits` and `target` |
| Extra-nonce assignment | Pool partitions coinbase metadata/nonce search space and recalculates commitments |
| Share submission and duplicate detection | Pool validates share against its target; Core only accepts complete solved blocks |
| Block construction | Core returns payout, reward outputs, ordered transaction hex and header inputs; pool builds canonical bytes |
| Network block submission | `POST /mining/submit-block` legacy or full, followed by hash lookup |

The [public miner README's Chipcoin section](https://github.com/gacanga/crypto-connection-miner#chipcoin-chc) describes a **pool-specific Bitcoin Stratum V1-like dialect**:

| Method | Publicly documented worker-facing data |
| --- | --- |
| `mining.subscribe` | Subscription result with `extranonce1` of 2 bytes (4 hex digits) and extranonce2 size 2 bytes. |
| `mining.authorize` | The client sends its configured worker name and password. The public README describes a CHCQ payout address as the username; the client does not enforce that policy. A production operator reports the server policy below; server source remains unaudited. |
| `mining.notify` | `[job, previous hash in reversed 4-byte words, coinb1, coinb2, Merkle branches, version, bits, time, clean]`. |
| `mining.set_difficulty` | `[d]`. The client computes its share target from Bitcoin `diff1 / d`, with `diff1 = 0x00000000ffff0000...0000`. The public README rounds this to `2^224 / d`; the two values are not identical. This is **not** Core network difficulty. |
| `mining.submit` | `[worker, job, extranonce2, time, nonce]`. |

The [CPU client](https://github.com/gacanga/crypto-connection-miner/blob/6d40215d6e070c3022e8abc7380e5b969b98e7ad/cpu/ccm_cpu.cpp) and [GPU client](https://github.com/gacanga/crypto-connection-miner/blob/6d40215d6e070c3022e8abc7380e5b969b98e7ad/gpu/gostminer.cu) parse `mining.notify`, send `mining.subscribe`/`mining.authorize`/`mining.submit`, concatenate `coinb1 || extranonce1 || extranonce2 || coinb2`, compute double-SHA256 coinbase/branch hashes, and build an 80-byte header. Both compare the SHA-256d digest as a big-endian integer. With a 2-byte extranonce2, both allocate its upper four bits to a worker slot and lower twelve bits to a counter. The public README says the pool places these four extranonce bytes in the coinbase's `locktime`; the client itself only inserts them between the two supplied coinbase fragments and does not verify their transaction offset. The [fixture](test-vectors/v1.json) includes a locktime mutation to verify that changing it changes TXID and Merkle root. **These Stratum field conventions belong to this external miner/pool implementation; they are not standardized by Chipcoin Core.** Do not send Bitcoin coinbase/script or Bitcoin Merkle byte reversals to Chipcoin without adapting to [`serialize_transaction`](../../src/chipcoin/consensus/serialization.py), [`merkle_root`](../../src/chipcoin/consensus/merkle.py), and [`hash_to_int`](../../src/chipcoin/consensus/hashes.py).

## Crypto Connection Miningcore v6.1 — in production (Julien's report)

Julien reports the following for Crypto Connection's Miningcore Chipcoin module v6.1 and its separate job manager. They describe **that backend only**. The server source and exact worker-to-block bytes have not been independently verified.

| Topic | Operator-reported behavior |
| --- | --- |
| Worker protocol | Bitcoin Stratum V1; no version rolling. `mining.subscribe` returns a 2-byte extranonce1 assigned per connection and an extranonce2 size of 2 bytes. |
| Authorization | Username is a CHCQ address with optional `.worker` suffix; password is `x` or `d=N` for static difficulty. An invalid-address login returns error `24` and triggers a temporary IP ban. Julien reports that **since 2026-11-24 21:22 UTC**, Miningcore v6.1 authorizes a worker only if its address has version `0x50`, scheme ID `0x0a`, and ML-DSA-44. This is pool admission policy, not a Core error code or a new consensus rule. |
| Coinbase split | `coinb1` holds canonical version, zero-input count, output count and the template's exact encoded outputs. The four extranonce bytes (`extranonce1 || extranonce2`) occupy the little-endian `uint32` coinbase `locktime`; `coinb2` holds metadata encoded in sorted key order, including `coinbase`, `height`, and an extra `miner_id` key. The resulting locktime is normally nonzero. See [coinbase serialization](COINBASE_AND_PAYOUTS.md). |
| Job lifecycle | One Core template per Stratum job. A pool counter is the worker-visible job ID; the opaque Core `template_id` stays with that job. Tip hash is polled from `GET /v1/tip` every 500 ms. A tip change triggers a new template and invalidates old jobs; every 10 s on an unchanged tip a new template/job is sent with `clean_jobs=false`. The newest four jobs are retained. The `clean_jobs` value sent **at a tip change** is not yet confirmed. These are pool scheduling choices, not Core guarantees. |
| Share policy | Pool target is reported as `2^224 / d`; the reviewed miner client calculates `((2^224 - 2^208) / d)` from Bitcoin diff1. The client target is smaller by `1/65536` (about **0.00152588%**) relative to the pool's idealized target, so that client searches slightly harder. Pool accepts `ntime` from template `curtime` through its current time plus 7200 s. Duplicate key is `(job, extranonce1, extranonce2, ntime, nonce)`. These are pool acceptance rules; Core still enforces network timestamp, bits and PoW rules. |
| Hashrate | Julien reports that Crypto Connection estimates hashrate from **the sum of accepted share difficulties** over its observation window, rather than from the number of shares alone. The window duration was not supplied. This is a pool statistic, not a Core network-hashrate rule. |
| Submission | The backend uses **legacy** submission with each job's `template_id`. After `unknown_or_expired_template`, an older recovery path requested a fresh template and reused the solved bytes with a new ID only after comparing previous hash, bits, outputs and ordered TXIDs. Julien reports that **since 2026-11-24 23:16 UTC**, Miningcore v6.1 also runs a full-block fallback: query `GET /v1/tip`, compare candidate parent with current tip, submit the unchanged complete block without `template_id` only if equal, then check the block at its height for active-chain hash inclusion. A matching tip is a race-sensitive precheck, not an acceptance guarantee. The fallback is this pool's policy, not mandatory for other pools. See [submission](BLOCK_SUBMISSION.md). |
| Reorg and payout policy | Any tip-hash change drops jobs. The backend checks `GET /v1/block?height=H`; it calls its block confirmed when the hash matches with **101 confirmations**, and classifies it as orphaned for accounting if a competing block at `H` is six blocks deep. These thresholds are pool policies, not consensus finality. For PPLNS, the miner coinbase output goes to a pool CHCQ wallet and miners receive later ML-DSA-44-signed v2 payments after maturity. |

The Core's legacy cache expires records after **15 seconds** and holds at most **256** templates in tagged v0.1.2. These are fixed values in [`NodeService`](../../src/chipcoin/node/service.py), not a reported pool setting. A new template on the same tip does not extend an older ID's TTL. A tip change clears cached IDs, so `unknown_or_expired_template` can mean tip invalidation rather than elapsed time; full-block submission avoids that cache requirement while preserving normal fork-choice and validation. See [templates](BLOCK_TEMPLATES.md) and [submission](BLOCK_SUBMISSION.md).

At each new Core template: retain the exact ordered transaction bytes and required coinbase outputs, allocate distinct extra-nonces, serialize the modified coinbase, hash to TXID, calculate Merkle root, serialize the 80-byte header, and distribute the worker fields in your own protocol. On share return, reconstruct the **same** header and check share difficulty. If the header also meets network target, serialize the complete block and submit it. For late shares, distinguish a pool-stale job from an expired legacy template and from a block still valid at the same chain tip. Full-block submission avoids template-ID cache dependence but never bypasses consensus.

Julien reports 12 node restarts in tests of the fallback: 3 blocks recovered, 5 stale solutions not resubmitted, and no side branch produced in those tests. These are operator-reported outcomes, not a locally reproduced test set; the counts do not establish a general recovery rate. He also reports a synthetic private-Devnet `chc_stratum_vector.json` with one accepted example and 68/68 byte-identical reconstructions, 41 accepted solutions and 27 second solutions stale at the same height. That file is not in this checkout, so its bytes, hashes and counts remain unverified here.

The [isolated pool regression](../../tests/integration/pool/test_block_submission.py) exercises block assembly and HTTP submit without asserting a Stratum wire contract. **Independent server-code and wire-vector verification remain open**, as do worker-level extranonce allocation/rotation details and the tip-change `clean_jobs` flag. An independent pool must validate its own backend and worker traces. The [Stratum vector checklist](STRATUM_VECTOR_REQUEST.md) lists the bytes needed before a pool-specific vector can be published.
