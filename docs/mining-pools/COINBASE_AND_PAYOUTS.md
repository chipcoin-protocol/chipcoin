# Coinbase and pool payouts

Source: [`build_coinbase_transaction`](../../src/chipcoin/node/mining.py), [`_validate_coinbase_distribution`](../../src/chipcoin/consensus/validation.py), [`subsidy_split_chipbits`](../../src/chipcoin/consensus/economics.py), [network parameters](../../src/chipcoin/consensus/params.py), and [reward settlement](../../src/chipcoin/consensus/epoch_settlement.py). This page describes tagged Core `0.1.2` at `12e4dbc8974bd76885e30e6dacdf1b7be898e126`.

The normal coinbase is transaction **version 1**, with no inputs, `locktime=0`, metadata containing `coinbase:"true"` and decimal `height`, and an ordered output list. Output 0 is the miner payout, exactly **base miner subsidy + included transaction fees**. Subsequent outputs, if any, are the deterministic rewarded-node recipients at an epoch-closing block with a valid included settlement. The template returns `coinbase_tx.outputs`, `node_reward_outputs`, `miner_reward_chipbits`, and `node_reward_total_chipbits`; preserve these amounts and ordering. The Core recomputes fees and distribution from chain state and transaction contents. A missing or incorrect required output fails contextual validation.

On Mainnet the epoch length is 100 blocks; [`is_epoch_reward_height`](../../src/chipcoin/consensus/economics.py) tests `(height + 1) % 100 == 0`. This is **not** every block whose printed height ends in `00`. Eligible reward recipients are derived from settlement data; a pool cannot choose them. The number of coinbase outputs must equal `1 + rewarded_node_count` for an included settlement, or exactly one when no rewarded outputs apply. `max_rewarded_nodes_per_epoch=25` bounds Mainnet rewarded entries, so at most 26 coinbase outputs are possible under this rule; Testnet and Devnet caps are 15 and 10 rewarded entries. The 4,000,000-unit block limit is the sum of serialized transaction byte lengths as defined by [`block_weight_units`](../../src/chipcoin/consensus/validation.py). There is no general permission to add arbitrary extra coinbase outputs.

The tagged [network parameters](../../src/chipcoin/consensus/params.py) start with a 50 CHC miner base subsidy per non-genesis block and a 50 CHC **scheduled epoch reward** at eligible epoch-closing heights. Both amounts halve by bit-shift every 111,000 heights and are clamped by the 11,000,000 CHC supply cap in [`subsidy_split_chipbits`](../../src/chipcoin/consensus/economics.py). The node reward is not an extra 50 CHC on every block; actual reward outputs require a valid included settlement and eligible recipients. At heights without rewarded outputs, do not mint a node payout. The miner output includes the fees from the transactions actually in the block. Mainnet, Testnet and Devnet share those initial subsidy and halving constants in this release, but have different maturity and reward-node activation heights; never substitute one profile's PoW or activation settings for another's.

Mainnet coinbase maturity is **100 blocks**: an output at height `H` is spendable in a transaction included at height `S` only if `S - H >= 100`. This applies to miner and rewarded-node coinbase outputs. On Testnet the configured maturity is 20; on Devnet it is 10. Reorgs can remove or reclassify outputs, so pool accounting must await a suitable chain depth and recheck inclusion.

**SOLO:** a pool can request a template with one controlled, ML-DSA-44 CHCQ payout address on Mainnet. The Core places that address in the single miner output. If it is the miner's address, this is a direct on-chain payout to that miner after coinbase maturity. Core does not determine which worker owns the address or implement the pool's SOLO accounting.

**PPLNS:** direct multiple-miner outputs in coinbase are **unsupported** by current consensus. The Core requires exactly one miner output plus deterministic reward-node outputs. A PPLNS pool can receive the miner output in a pool-controlled CHCQ wallet and later pay participants using standard, independently signed CHCQ transaction v2 payments after maturity. Pool accounting, fees, distribution and payout scheduling are external to Core. Never reinterpret reward-node outputs as miner-share outputs or promise immediate spendability.

Core does not mandate an `extra_nonce` byte length or a Stratum extranonce1/extranonce2 split. [`test_block_submission.py`](../../tests/integration/pool/test_block_submission.py) varies coinbase metadata; the [public Crypto Connection miner description](https://github.com/gacanga/crypto-connection-miner#chipcoin-chc) describes a separate pool dialect that places two 2-byte extra-nonces in the coinbase's 4-byte `locktime`. Both alter canonical transaction bytes, coinbase TXID, Merkle root and header hash. Core's metadata encoder sorts keys and length-prefixes UTF-8 strings; `locktime` is uint32 little-endian. The pool must partition its nonce space to avoid collisions and stay inside block weight and request-size limits.

At genesis, the canonical Mainnet transaction is an exceptional **output-free** coinbase committed by the embedded genesis block. Do not infer normal block payout rules from it; see the [genesis vector](test-vectors/v1.json).
